# 파티 채팅 문제 분석 보고서

2026-10-18 재검토 · 기준 커밋 `48df016` 및 현재 작업 트리

이 문서는 보고된 장애 현상과 현재 구현을 대조한 결과다. **재연결 시 참가자 식별이 끊기고 일시적 오류에서도 재시도를 포기한다는 핵심 지적은 타당하다.** 다만 안드로이드 IME 내부 동작, `crossws` Proxy, 초기 입장 중복 호출 등 일부 원인 설명은 코드와 재현 결과에 맞게 수정했다.

판정은 다음과 같이 구분한다.

- **확인**: 현재 코드에서 해당 동작과 발생 조건을 확인했다. 실행 재현까지 한 항목은 별도로 표시한다.
- **조건부 위험**: 특정 지연·장애·사용 패턴에서 발생하는 구조적 위험이다. 실제 운영에서의 빈도는 확인하지 않았다.
- **가설**: 기기·브라우저의 이벤트 로그나 실기기 재현이 더 필요하다.
- **정정**: 기존 설명을 그대로 결함의 원인으로 삼기 어렵거나, 현재 코드에 반대 근거가 있다.

우선순위는 P1(연결·참가자·기록의 일관성), P2(복구·사용성·장시간 안정성), P3(규약·검증 보완)로 구분한다. 운영 장애의 발생 빈도나 보안 취약점 점수를 뜻하지 않는다.

## 1. 안드로이드 멀티윈도우 한글 역순 분리 입력

### 보고된 증상과 확인 범위

`야 김별붕!`을 입력했는데 `!ㅇㅜㅂㄹㅕㅂㅁㅣㄱ ㅑㅇ`처럼 자모가 분리되어 역순으로 쌓이는 현상이다. 매 입력이 문자열 앞에 삽입되고 조합이 유지되지 않는 상황과 부합하지만, 결과 문자열만으로 커서 이동을 일으킨 코드나 브라우저 내부 동작까지 특정할 수는 없다.

**판정: IME 조합 중 DOM 변경 위험은 확인, 보고된 현상의 직접 원인은 가설.** 이번 검토에서는 해당 안드로이드 기기·키보드·멀티윈도우 환경을 재현하지 않았다.

### 코드에서 확인한 사실

- `app/pages/party/[roomId].vue:798`은 `UTextarea`, `v-model="draft"`, `autoresize`, `rows=1`, `maxrows=6`을 사용한다.
- 설치된 `@nuxt/ui 4.11.1`의 `node_modules/@nuxt/ui/dist/runtime/components/Textarea.vue:89,115,133,162`는 네이티브 `<textarea>`에 `:value`와 `@input`을 사용한다. `onInput`에서 `autoResize()`를 호출하고, 모델 변경 후에도 `nextTick(autoResize)`를 예약한다.
- `autoResize()`는 `rows`와 `style.overflow`를 바꾸고 `getComputedStyle`·`scrollHeight`를 읽는다. 일반적인 모델 변경 입력에서 리사이즈가 두 경로로 실행되며, 이 코드에 조합 중 리사이즈를 유예하는 처리는 없다.
- 반면 페이지의 Enter 전송 처리는 `event.isComposing`과 `keyCode === 229`를 검사한다(`app/pages/party/[roomId].vue:271`). IME 보호가 전혀 없다는 평가는 맞지 않는다.

### 기존 설명에서 정정할 부분

1. **“`:value`이므로 매 입력마다 값을 강제로 다시 쓰고 커서를 0으로 만든다”는 단정은 제외한다.** Vue 런타임은 기존 DOM 값과 새 값이 같으면 실제 `value` 할당을 생략할 수 있다. 리사이즈 호출의 존재와 IME 조합 해제 사이의 인과관계는 별도 검증이 필요하다.
2. **“멀티윈도우에서는 매 입력마다 `InputConnection`을 리셋한다”는 설명은 입증되지 않았다.** 기기·OS·브라우저·IME 버전과 `compositionstart/update/end`, `beforeinput/input`, `selectionStart/End` 로그가 필요하다.
3. **`interactive-widget=resizes-content`와 수동 inset이 항상 이중 적용되는 것은 아니다.** 이 설정은 Layout/Visual Viewport를 함께 줄인다. 따라서 `innerHeight - (visualViewport.offsetTop + visualViewport.height)`가 0에 가까울 수 있다. 현재 코드의 `bottom`·`marginBottom` 병행 및 viewport 이벤트 때의 스크롤 조작은 검증 대상이지만, 설정이 함께 있다는 이유만으로 원인을 확정해서는 안 된다. [Chrome 공식 viewport 설명](https://developer.chrome.com/blog/viewport-resize-behavior)

### 검증 및 개선 방향

같은 기기·키보드에서 전체 화면/분할 화면/팝업 창을 비교하고, `autoresize`만 끈 버전, 네이티브 `v-model` textarea, inset 처리를 끈 버전을 각각 대조한다. 조합·커서·viewport 로그로 문제가 사라지는 조건을 확인한 뒤 조합 중 리사이즈 유예와 레이아웃 처리를 결정한다. 원인 확인 전에 커서를 매번 끝으로 강제 이동하면 중간 문장 편집을 깨뜨릴 수 있다.

## 2. 반복되는 WebSocket 단절·재연결

### 2.1 클라이언트 heartbeat 종료 정책 — 조건부 위험 · P2

근거: `app/composables/party-chat.ts:93-110,212-221`.

- 소켓이 열리면 20초마다 `PING`을 보내고 `unansweredPings`를 증가시킨다. 응답 없이 두 번 전송한 뒤 다음 tick에 연결을 닫는다. 정상적인 타이머 실행 기준으로 첫 ping은 20초, 두 번째는 40초, 종료는 60초 시점이다.
- **`PONG`뿐 아니라 모든 `onmessage` 수신이 카운터를 0으로 만든다.** 따라서 정상 채팅을 계속 수신하는 연결이 단순히 PONG만 늦어져 끊기는 구조는 아니다.
- 브라우저 정지·절전·네트워크 단절 후 복귀 시 타이머와 수신 이벤트의 처리 순서에 따라 연결을 불필요하게 닫을 가능성은 있다. 하지만 지연된 interval이 모두 몰아서 실행된다는 설명이나, 백그라운드 전환만으로 반드시 실패한다는 주장은 제외한다. Chrome의 타이머 제한에도 조건과 예외가 있다. [Chrome 타이머 제한 설명](https://developer.chrome.com/blog/timer-throttling-in-chrome-88)
- `visibilitychange`·`online` 복귀 시 연결을 재검증하는 별도 경로가 없고, close code에 따른 복구 정책도 없다.

개선: 마지막 수신 시각을 바탕으로 판정하고, 복귀 시 유예 시간을 둔 연결 검사를 수행한다. 종료 코드와 마지막 송수신·가시성 시각을 남겨 실제 원인을 구분한다.

### 2.2 DB 지연을 소켓 종료로 확대 — 확인 · P1

근거: `app/composables/party-chat.ts:93,117-118,285-290`, `server/utils/party-chat.ts:266-276,624-638,767-784`, `server/utils/database.ts:29-34`.

- 채팅 전송 후 10초 안에 확인을 받지 못하면 임시 메시지를 `unconfirmed`로 바꾸고 **전체 소켓을 닫는다**.
- 서버는 방별 `writeQueue`에서 DB 저장을 완료한 뒤 메시지를 브로드캐스트한다. DB 지연과 큐 적체가 곧 전송 확인 지연으로 이어진다.
- 입장도 동일하다. 클라이언트의 연결 타이머는 TCP/WebSocket open 때가 아니라 **`JOINED` 수신 때 해제**된다. 연결 자체는 열렸어도 참가자 저장·방 TTL 갱신이 10초를 넘으면 소켓을 닫는다.
- DB 풀은 `max: 5`이고 연결 시도 제한은 15초다. 모든 정상 DB 작업이 클라이언트의 10초 예산 안에 끝난다고 보장되지 않는다.
- 새 입장·퇴장 저장이 추가되어 지연을 악화할 수 있다. 다만 실제 재연결 폭풍의 빈도·규모는 부하 측정이 필요하다.

개선: 전송 결과 미확정과 연결 장애를 분리하고, 입장·메시지 확인·heartbeat의 시간 예산을 각각 정한다. 서버 메시지 멱등성(4.4)과 참가자 승계(3장)를 함께 설계해야 안전한 재시도가 가능하다.

### 2.3 `crossws` Proxy가 pong·bufferedAmount를 깨뜨린다는 설명 — 정정

근거: `server/routes/ws/party.ts:101-127,265-272`, `server/utils/party-chat.ts:357-404,524-536`, 설치된 Nitro 2.13.4가 사용하는 `crossws 0.3.5` Node 어댑터 및 `ws` 구현.

`peer.websocket`이 Proxy라는 사실은 맞지만, 기존 설명의 `_socket === undefined` 또는 `_events` 분리 결론은 성립하지 않는다. `Reflect.get(target, prop)`는 getter를 원본 target을 receiver로 실행하고, 별도의 set trap도 없다. 설치된 `crossws` Peer·`ws` 객체 검증에서 `bufferedAmount=10`, 원본의 pong 이벤트 수신 1회, 동일한 `_events` 객체를 확인했다. 따라서 이 가정을 전제로 원본 소켓에 우회 접근하는 수정은 우선하지 않는다.

또한 다음 방어가 이미 있다.

- 서버는 참가자에게 30초 간격으로 WebSocket ping을 보내고 pong 리스너에서 `lastSeenAt`을 갱신한다.
- `consumePartyMessage()`는 수신 메시지를 처리할 때 이미 `lastSeenAt`을 갱신한다. “PING 외의 유효 프레임에도 갱신을 추가해야 한다”는 원래 제안은 중복이다.
- heartbeat 만료는 `90초 초과`를 30초 주기 유지보수에서 검사한다. 정확히 90초에 항상 종료되는 것은 아니다.
- Nginx `proxy_read_timeout 120s`는 무조건적인 연결 수명 제한이 아니다. 서버 ping 데이터가 정상적으로 흐르면 read timeout도 갱신된다. [Nginx WebSocket 공식 문서](https://nginx.org/en/docs/http/websocket.html)

배포 어댑터나 의존성을 변경할 때 ping/pong·전송 버퍼를 통합 검증하는 것은 필요하지만, 현재 Proxy를 반복 단절의 확정 원인으로 분류하지 않는다.

## 3. 사용자 복제·닉네임 충돌과 참가자 식별 단절

### 3.A 이전 연결이 남아 있을 때 재연결을 포기 — 확인 · P1

근거: `shared/types/party.ts:72-78`, `app/composables/party-chat.ts:97,186-207`, `app/pages/party/[roomId].vue:95-100`, `server/utils/party-chat.ts:603-640`.

1. 네트워크 전환 등으로 클라이언트가 연결을 잃어도 서버에는 이전 연결이 잠시 남을 수 있다.
2. 클라이언트는 새 소켓에서 같은 닉네임으로 `JOIN`한다. 프로토콜에는 이전 참가자임을 증명하는 재연결 토큰이 없다.
3. 이전 참가자가 닉네임을 점유하고 있으면 서버는 `NICKNAME_TAKEN`을 반환한다.
4. 클라이언트는 연결 완료 전 **모든 `ERROR`**에 `stopped=true`, `joined=false`, 메시지·참여자 초기화, 소켓 종료를 수행한다. 자동 재시도는 멈춘다.
5. 페이지는 `NICKNAME_TAKEN`에서 닉네임 모달을 연다. 다른 닉네임으로 입장하면 이전 연결이 정리될 때까지 참여자 두 명처럼 보일 수 있다.

같은 닉네임을 동시에 허용해서 생기는 복제가 아니라 **연결마다 독립된 사용자로 취급하는 구조**다. 서버의 닉네임 중복 검사 자체는 입장 큐 안에서도 다시 수행한다.

개선: 서버가 발급·검증하는 충분히 예측 불가능한 재연결 토큰을 방 세션·참가자에 결합하고, 승계할 때 이전 소켓을 무효화한다. **닉네임이나 공개된 `participantId`만으로 승계를 허용하면 다른 사람이 참가자를 탈취할 수 있다.** 토큰 보관 범위와 같은 사용자의 여러 탭 처리도 명시해야 한다.

### 3.B 재연결마다 새 참가자 ID 생성 — 확인 · P1

근거: `server/utils/party-chat.ts:618-631`, `server/utils/party-chat-storage.ts:134-147`, `app/composables/party-chat.ts:124,167-184`.

성공적인 입장마다 `randomUUID()`로 새 참가자를 저장한다. 초기 입장 후 N번 재연결하면 N+1개의 참가자 행이 남는다. 과거 메시지의 외래키를 보존하기 위해 이전 행을 남기는 것 자체는 정상이나, 동일 사용자의 재연결과 새 입장을 구별하지 못한다.

그 결과 이전 메시지 작성자는 현재 참가자 목록에 없는 사용자로 보이고, 새 참가자의 캐릭터·순서 변경이 이전 참가자의 메시지에는 반영되지 않는다. 정상 재연결에서도 재현 가능한 식별 문제다. 3.A의 인증된 승계와 짧은 재접속 유예로 해결해야 한다.

### 3.C 기존 경합 설명에서 구분할 사항

- **클라이언트 초기 입장 중복은 기존 설명만으로 성립하지 않는다.** `watch([room, profileReady])`는 `status === 'idle'`일 때만 입장하고(`app/pages/party/[roomId].vue:91`), `enterRoom()`은 `connecting` 상태를 막는다(`:162`). 직접 호출한 `join()`은 `connect()`에서 동기적으로 상태를 바꾼다. watcher·직접 호출·`refreshRoom()`이 함께 있다는 이유만으로 두 소켓이 생성된다고 판단하면 안 된다.
- **서버는 입장 중 닫힌 연결을 재검사한다.** 입장 큐의 DB 작업 전후 `connection.closed`를 검사한다(`server/utils/party-chat.ts:624-629`). 닫힌 연결이 항상 참가자로 등록된다는 설명은 맞지 않는다.
- 입·퇴장 메시지 저장은 같은 `writeQueue`에 들어가므로 “입장 저장을 기다리는 동안 닫히면 퇴장 기록이 먼저 저장된다”는 일반화도 맞지 않는다. 실제로 확인한 문제는 입장 공지 저장 후 참조 오류(4.13), 서버의 동시 JOIN(4.11), 페이지 이탈 후 늦은 입장(4.10)이다.

## 4. 추가 문제와 기존 잠재 문제 재평가

### 4.1 재연결마다 입·퇴장 알림 누적 — 확인 · P2

근거: `server/routes/ws/party.ts:209-224`, `server/utils/party-chat.ts:251-264,652-663,837-846`.

네트워크 순단과 명시적 퇴장을 구별하지 않고 `LEAVE_NOTICE`·`JOIN_NOTICE`를 저장한다. 반복 재접속은 대화를 알림으로 채우며 최근 300개/256KiB의 **메모리 기록**에서 실제 대화를 밀어낸다. DB 기록은 방 세션 만료까지 남으므로 즉각적인 영구 삭제로 표현해서는 안 된다. 인증된 재연결 승계와 유예 기간을 도입하고, UI에서는 연속 알림을 묶을 수 있다.

### 4.2 IP 제한과 복구 불가능한 오류 상태 — 확인 · P1

근거: `server/api/party/rooms.post.ts:16-49`, `server/utils/party-chat.ts:313-325,593-600`, `app/composables/party-chat.ts:197-207`.

HTTP 방 열기와 WS `JOIN`은 **각각 별도 카운터로 IP당 1분 12회**다. 두 요청이 하나의 공통 12회를 나눠 쓰는 것은 아니다. 동일 NAT의 여러 사용자나 반복 재연결은 각 제한에 도달할 수 있다. `JOIN_RATE_LIMITED`나 `STORAGE_UNAVAILABLE`도 연결 전 오류 처리에서 영구 재시도 중단으로 바뀐다.

고정된 백오프에는 jitter가 없고, 한 번 `JOINED`를 받으면 재시도 횟수가 0으로 초기화된다. 짧게 연결되었다 끊기는 다수의 클라이언트가 비슷한 시점에 다시 입장할 수 있다(`app/composables/party-chat.ts:119,221`).

개선: 재시도 가능한 오류와 입력 수정이 필요한 오류를 구별하고, 제한 해제 시각/`retryAfter`와 jitter를 사용한다. 같은 참가자의 인증된 재연결과 새 입장의 제한도 분리 검토한다.

### 4.3 재연결 시 이미 불러온 이전 기록 교체 — 확인 · P2

근거: `app/composables/party-chat.ts:125-139`.

`JOINED`가 오면 `messages = [...data.messages, ...unresolved]`로 전체 배열을 교체하고 `loadedHistory=false`로 바꾼다. 같은 방 세션이어도 이미 불러온 과거 대화가 사라지고, 스크롤 기준점도 달라질 수 있다. DB에서 삭제된 것은 아니며 다시 조회해야 한다.

개선: **동일 `sessionId`일 때만** 서버 메시지 ID로 기존 확정 기록과 병합하고, 다른 세션이면 이전 기록을 분리한다. 같은 6자리 방 번호가 재사용되었다고 이전 세션 기록까지 섞어서는 안 된다. 재연결 중 놓친 구간과 임시 메시지의 정렬·확정도 함께 처리한다.

### 4.4 낙관적 메시지 매칭 설명 정정 및 재전송 중복 — 확인 · P2

근거: `app/composables/party-chat.ts:70-84,125-133,154-160,264,294-298`, `server/utils/party-chat.ts:767-779`, `server/utils/party-chat-storage.ts:150-157`, `database/migrations/0012_party_chat_history.sql`.

**기존 주장 정정:** 실시간 `appendMessage()`는 작성자 ID까지 비교하지만, `JOINED`에서는 수신 기록의 `clientMessageId` 집합으로 이전 임시 메시지를 제거한다. 서버에 저장된 이전 참가자의 메시지가 `JOINED.messages`에 포함되면 새 참가자 ID를 받아도 정상 대조된다. 모의 소켓 재연결로 이 경로를 확인했다. 기록이 최근 범위 밖이면 미확정 상태로 남을 수 있으나, 원인을 단순히 참가자 ID 불일치로 설명할 수는 없다.

**실제 제약:** 서버는 같은 참가자가 동일 `clientMessageId`로 다시 전송해도 새로운 서버 메시지 UUID를 발급해 다시 저장한다. DB의 `ON CONFLICT (id)`는 서버 UUID만 보호하며, 클라이언트 메시지 ID에 대한 고유 제약은 없다. 메모리 저장소를 주입한 실행에서 동일 요청이 서로 다른 서버 ID의 채팅 2건으로 저장됨을 확인했다. 웹의 “다시 입력”도 새 `clientMessageId`로 보내므로 중복 방지는 되지 않는다. UI가 중복 가능성을 경고하는 것은 타당하다.

추가로 `JOINED`·`HISTORY`의 확인 집합과 send timer 정리는 작성자 없이 `clientMessageId`만 사용한다. 기본 웹 클라이언트의 UUID 충돌 가능성은 낮지만, 외부 클라이언트가 같은 값을 쓰면 다른 작성자의 메시지로 내 임시 메시지를 정리할 수 있다. 재전송 보호와 대조 키는 방 세션·안정된 참가자·클라이언트 메시지 ID로 통일하는 편이 안전하다.

### 4.5 PiP 창 밖에 표시되는 닉네임 모달 — 확인 · P2

근거: `app/pages/party/[roomId].vue:833-840`, 해당 페이지의 `useDefaultOverlayPortal`과 `USlideover` 설정.

캐릭터·참가자 패널은 PiP 포털 처리가 있지만 닉네임 모달은 채팅 화면의 `<Teleport>` 밖에 있고 별도 포털 설정도 없다. PiP 중 재연결에서 닉네임 충돌이 나면 실제 입력 모달은 원래 탭에 열린다. 모달도 PiP 문서로 이동하는 렌더링 트리에 포함하거나 명시적인 대상에 포털하고, focus trap과 닫힘 동작을 함께 확인해야 한다.

복구 UI에도 영향이 있다. PiP 복귀 버튼은 `joined && pipSupported` 조건이므로 오류로 `joined=false`가 되면 사라진다(`app/pages/party/[roomId].vue:478`). 또한 PiP 스타일 동기화는 원본 `body.style.cssText` 전체를 복사한다(`app/composables/party-picture-in-picture.ts:51` 이후). 원본 모달의 `pointer-events:none` 같은 입력 잠금 스타일도 전달될 수 있으므로 실제 PiP 테스트에서 확인해야 한다.

### 4.6 DB TTL 갱신 실패 — 조건을 좁혀 정정 · P2

근거: `server/utils/party-chat.ts:395-399,427-436`, `server/utils/party-chat-storage.ts:94-116,120-130,191-214`, `server/plugins/party-chat-cleanup.ts:5-7`.

현재 프로세스에 방이 있으면 `findPartyRoom()`은 DB 만료 확인 없이 메모리 방을 반환한다. DB 정리 작업도 메모리에 보유한 세션을 제외한다. 따라서 한 번의 `extendRoom()` 실패로 활성 방이 즉시 `ROOM_NOT_FOUND`가 된다는 기존 설명은 과장이다.

다만 **갱신 실패가 남은 TTL을 넘게 지속되고 프로세스가 재시작되면**, DB에는 이미 만료된 세션이 남을 수 있다. 직접 WS 재입장은 `findRoom()`에서 거절되고, HTTP 방 열기는 만료 세션을 지우고 새 세션을 만든다. 이전 기록이 삭제될 수 있는 조건이다. 장시간 DB 장애 후 복구·재시작 시나리오를 별도 검증하고, 갱신 실패 관측과 세션 복구 정책을 마련해야 한다. 현재 문서상 단일 프로세스 운영 전제를 다중 인스턴스로 확장할 때도 TTL 소유권 설계가 필요하다.

### 4.7 [신규] 빈 방의 첫 참가자는 잘린 과거 기록을 조회할 수 없음 — 실행 재현 · P2

근거: `app/composables/party-chat.ts:82-83,134,242-245,274-275`, `app/pages/party/[roomId].vue:291`.

1. 새 방의 첫 `JOINED.messages`는 비어 있고, 자신의 `JOIN_NOTICE`는 그 이후에 온다. 이때 `hasOlder=false`가 된다.
2. 이후 채팅·알림을 300개 넘게 받으면 클라이언트는 오래된 항목을 잘라낸다.
3. 이때 `hasOlder`를 갱신하지 않으므로 DB에 과거 기록이 있어도 스크롤 조회와 `loadOlder()`가 모두 차단된다.

모의 소켓에서 빈 `JOINED` 이후 301건을 전달했을 때 화면 배열 300건, `hasOlder=false`, `loadOlder() === false`임을 확인했다. 메시지를 잘라냈다면 이전 기록이 존재함을 상태에 반영하거나, 서버가 명시적인 이력 커서를 제공해야 한다.

### 4.8 [신규] 이전 대화 조회 후 클라이언트 메모리·DOM 무제한 증가 — 실행 재현 · P2

근거: `app/composables/party-chat.ts:83,161,169-176,275`, `app/pages/party/[roomId].vue:729`의 메시지 갱신·렌더링 경로.

`HISTORY` 응답을 한 번만 받아도 `loadedHistory=true`가 되고, 이후에는 최근 300개로 자르지 않는다. 응답이 빈 배열이고 `hasMore=false`여도 동일하다. 모의 소켓에서 빈 HISTORY 응답 뒤 총 651건이 계속 보관되는 것을 확인했다.

페이지는 모든 메시지를 `v-for`로 렌더링하고, 참가자 변경 때는 메시지 전체를 순회한다(`app/composables/party-chat.ts:169-176`). 장시간 채팅과 반복 이력 조회에서 메모리·DOM·갱신 비용이 계속 커진다. 과거 기록을 유지하려는 의도 자체는 타당하므로 단순 삭제 대신 가상 스크롤, 보관 예산, 재조회 가능한 페이지 단위 캐시를 함께 설계한다.

### 4.9 [신규] 웹과 서버의 글자 수 기준 불일치 — 확인 · P3

근거: `app/pages/party/[roomId].vue:88,165,182,803,852`, `app/composables/party-chat.ts:261`, `server/utils/party-chat.ts:182-184,193-224`.

웹의 `.length`와 HTML `maxlength`는 UTF-16 코드 단위를 기준으로 하지만 서버는 `Array.from(text).length`로 코드 포인트를 센다. 예를 들어 `😀` 501개는 서버 기준 501자로 허용되지만 웹에서는 1,002로 계산해 1,000자 제한을 넘는다. 닉네임 20자 제한도 동일하게 어긋난다. 결합 문자·가족 이모지 등의 사용자 인식 글자 수는 이 두 기준과도 다르다.

규약이 코드 포인트인지 표시상 글자 수인지 정하고, 입력 제한·검증·안내를 일치시킨다. 서버 검증을 우회하는 결함은 아니며 클라이언트 간 사용성 차이다.

### 4.10 [신규] 페이지를 떠난 뒤 늦은 응답이 유령 연결을 생성 — 실행 재현 · P1

근거: `app/pages/party/[roomId].vue:179-207`, `app/composables/party-chat.ts:225-239,325-331`.

1. 공유 링크의 닉네임 모달에서 입장을 요청하고, HTTP 응답이 오기 전에 다른 페이지로 이동한다.
2. unmount 정리는 `stopped=true`로 만들고 당시 소켓을 닫는다.
3. 늦게 도착한 `$fetch` 성공 응답이 계속 실행되어 `enterRoom()` → `join()`을 호출한다.
4. `join()`이 `stopped=false`로 되돌리고 새 소켓을 연다. 화면은 이미 없어졌으므로 이 소켓을 정리할 다음 unmount도 없다.

실제 함수·Vue와 모의 HTTP/WebSocket을 사용해 **요청 → unmount → 응답 → 새 소켓 생성·JOIN 전송**을 재현했다. 네트워크가 정상이라면 숨은 연결이 heartbeat를 계속 보내면서 닉네임과 참가자 자리를 점유할 수 있다. 새 페이지에서 같은 닉네임으로 입장하면 충돌하는 추가 원인이다.

개선: 요청 취소와 컴포넌트 생존 여부 검사를 추가하고, composable에는 재연결 중단과 별개인 영구 `disposed` 상태를 두어 unmount 이후 `join/connect`를 거절한다.

### 4.11 [신규] 같은 소켓의 동시 JOIN으로 여러 방에 유령 참가자 잔류 — 실행 재현 · P1

근거: `server/utils/party-chat.ts:552-558,603,624-633,811-843`, `crossws 0.3.5/dist/adapters/node.mjs:29-33`.

`ALREADY_JOINED` 검사는 첫 `await` 이전에만 있고, 입장 큐 내부에서는 닉네임 중복과 `closed`만 재검사한다. Node 어댑터도 한 message hook의 비동기 완료를 기다린 뒤 다음 메시지를 처리하는 구조가 아니다.

같은 peer가 서로 다른 방 A·B에 동시에 입장하도록 `Promise.all([join(A), join(B)])`을 실행하면 **둘 다 성공**한다. 두 방이 같은 mutable connection 객체를 보관하므로 A의 참가자 정보도 B의 정보로 바뀐다. 연결을 종료하면 마지막 `connection.room`인 B만 정리되고 A에는 peer가 남는다. 전역 연결 목록에서는 이미 제거되어 heartbeat 정리도 이 참가자를 찾지 못한다.

현재 웹 UI는 한 소켓에서 JOIN을 한 번 보내므로 정상 UI의 초기 watcher 중복과는 다른 문제다. 외부 WebSocket 클라이언트나 중복 프레임에서 서버 불변식이 깨지며, 방이 빈 것으로 판정되지 않아 만료되지 않는 결과로 이어질 수 있다.

개선: 연결 단위의 `joining/joined` 상태를 await 전에 예약하고 실패 시 해제한다. 큐 안에서도 현재 참가 상태와 연결 세대를 재검사한다. **방별 큐만으로 서로 다른 방의 동시 JOIN을 막을 수는 없다.**

### 4.12 [신규] 캐릭터·순서 동시 변경으로 저장 상태와 참가자 상태 불일치 — 실행 재현 · P2

근거: `server/utils/party-chat.ts:666-713`.

캐릭터·순서 변경은 **검증과 참가자 복사**를 큐 밖에서 수행한 뒤 DB UPDATE만 큐에 넣고, await 이후 메모리를 갱신한다. 따라서 SQL 실행 순서가 직렬이어도 각 요청의 입력 스냅샷은 오래된 상태일 수 있다.

재현: `101/P1` 참가자의 `SET_CHARACTER spectator` 저장을 지연시킨 상태에서 `SET_ORDER P2`를 처리한다. 두 번째 요청은 아직 `101/P1`을 보고 검증·복사한다. 작업 완료 후 **메모리는 `spectator/P2`, 저장소에 전달된 최종 상태는 `101/P2`**가 된다. 관전자는 순서가 없어야 한다는 규칙도 깨지고, DB에서 읽은 과거 기록과 현재 참가자 표시가 달라질 수 있다.

개선: 최신 참가 상태 확인, 검증, 스냅샷 생성, DB 저장, 메모리 갱신을 같은 직렬 작업 안에서 수행한다. 대기 중 연결이 종료될 가능성도 재검사한다.

### 4.13 [신규] 입장 공지 저장 중 종료하면 TypeError와 실시간 공지 누락 — 실행 재현 · P2

근거: `server/utils/party-chat.ts:652-663,842-843`, `server/routes/ws/party.ts`의 `recordPartyJoin()` 예외 처리.

`recordPartyJoin()`은 `await persistRoomMessage(connection.room, notice)` 뒤에 다시 `connection.room.participants`를 읽는다. 저장 대기 중 `removePartyConnection()`이 실행되면 `connection.room`이 `undefined`로 지워져 참조 오류가 발생한다.

입장 공지 저장을 지연시키고 연결을 제거한 뒤 저장을 재개하면 `Cannot read properties of undefined (reading 'participants')`가 발생한다. **저장 순서는 `join → leave`로 정상**이지만, 라우트의 catch가 로그만 남기고 반환하므로 입장 공지의 실시간 방송이 생략된다. 기존 3.C의 “저장 순서 역전” 대신 이 경로를 결함으로 기록한다.

개선: await 이후 접근할 방 객체를 안정적으로 보관하고, 이미 퇴장한 경우 공지 방송 여부를 명시적으로 결정한다. `changePartyCharacter/Order`에도 await 이후 연결 객체 접근이 있으므로 같은 종료 경합 검사가 필요하다.

### 4.14 [신규] 늦은 초기 방 조회 실패가 이미 연결된 채팅을 숨김 — 조건부 위험 · P2

근거: `app/pages/party/[roomId].vue:18-25,128,191-198,645-687`, 설치된 Nuxt `dist/app/composables/asyncData.js`의 오류 처리.

공유 링크 진입 시 초기 `refreshRoom()`과 닉네임 제출의 `$fetch`는 독립된 HTTP 요청이다. 닉네임 요청이 먼저 성공해 `room.value`를 채우고 WS 입장까지 완료한 뒤, 지연 중이던 초기 조회가 실패할 수 있다.

Nuxt의 async-data 오류 처리는 data를 기본값으로 되돌리므로 같은 `room` ref가 비워진다. 템플릿은 `joined`보다 `!room` 분기를 먼저 검사해, 소켓은 연결되어 있는데 “채팅방을 열지 못했습니다” 화면을 표시할 수 있다. 코드 경로는 확인했으며 실제 HTTP 지연을 주입한 통합 재현은 하지 않았다.

개선: 초기 방 열기와 닉네임 검증 요청의 결과 소유권을 통일하거나 요청 세대로 오래된 결과를 무시한다. 이미 연결된 세션의 화면 상태를 초기 조회의 늦은 실패가 덮어쓰지 않도록 한다.

## 5. 개선 우선순위

1. **P1: 재연결 복구 정책과 참가자 승계.** 인증된 토큰, 이전 연결 무효화, 재접속 유예, 일시적 오류 재시도와 jitter를 함께 구현한다.
2. **P1: 연결 생명주기 경합 차단.** 페이지 이탈 후 입장과 같은 소켓의 동시 JOIN을 막는다. 이 두 경로도 유령 참가자를 만드는 직접 원인이다.
3. **P1: 연결 상태와 저장 상태의 분리.** 10초 지연만으로 소켓을 닫지 않도록 하고 입장 큐·DB 지연을 관측한다. 재시도하려면 메시지 멱등성을 먼저 확보한다.
4. **P2: 서버 상태 변경의 원자성.** 캐릭터·순서 변경을 검증부터 메모리 반영까지 직렬화하고, 입장 공지 저장 중 종료 경합을 처리한다.
5. **P2: 기록 조회·화면 상태 수정.** 첫 참가자의 `hasOlder`, 같은 세션 재연결 병합, 클라이언트 보관 예산과 늦은 HTTP 오류 처리를 보완한다.
6. **P2: PiP 모달과 모바일 입력 검증.** 포털 구조는 수정 대상으로 확정하되, 한글 역순 현상은 실기기 대조 실험으로 리사이즈·viewport·IME 원인을 좁힌다.
7. **P3: 길이 규약과 자동 회귀 검증.** 클라이언트·서버의 문자 계산을 맞추고 아래 시나리오를 회귀 검사에 넣는다.

`crossws` Proxy 우회와 공개 `participantId`만 사용하는 참가자 승계는 현재 분석에 근거한 우선 해결책으로 삼지 않는다.

## 6. 검증 결과와 남은 검증

### 이번 검토에서 수행한 검증

- `pnpm test:party:rooms`: **12개 모두 통과**. 메모리 저장소를 사용한 서버 방 생명주기·기록·검증 로직 테스트다.
- 실제 `usePartyChat()` 소스를 TypeScript로 변환하고 모의 WebSocket·타이머를 주입하여 4.7·4.8을 재현하고, 일반 재연결에서 과거 참가자의 낙관적 메시지가 확인되는 경로를 검증했다.
- 실제 서버 함수에 메모리 저장소를 주입해 동일 `clientMessageId` 재전송이 두 건으로 저장되는 것과 이모지 길이 검증을 확인했다.
- HTTP 응답을 지연시킨 모의 환경에서 페이지 unmount 후 새 소켓이 생성되는 경로를 재현했다. 반대로 초기 조회와 닉네임 응답의 순서를 바꾼 정상 입장 두 경우에서는 소켓이 각각 1개만 생성됐다.
- 메모리 저장소의 작업을 지연시켜 같은 소켓의 동시 JOIN, 캐릭터·순서 동시 변경, 입장 공지 저장 중 종료 경합을 재현했다. 저장 상태 불일치 검증은 실제 PostgreSQL이 아닌 주입한 저장소 기준이다.
- 설치된 `crossws`·`ws` 객체로 Proxy의 bufferedAmount·pong 이벤트 처리를 확인했다. Vue DOM 패치 함수에는 동일 값을 전달했을 때 value setter 호출이 0회였다.
- `node --check scripts/test-party-chat.mjs`, `node --check scripts/test-party-storage.mjs`: 문법 검사 통과.
- 소스·설치된 라이브러리·DB 마이그레이션·Nginx/Compose 설정을 대조했다. 애플리케이션 구현은 수정하지 않았다.

### 검증 범위의 한계와 권장 회귀 시나리오

이번 검토에서 안드로이드 실기기, 실제 PiP 창 조작, 운영 네트워크·PostgreSQL 지연 주입은 수행하지 않았다. `test:party`·`test:party:storage`의 실제 HTTP/WS/DB 통합 실행도 수행하지 않았다. 위의 코드 확인·모의 재현을 실기기 또는 운영 장애 재현으로 해석하면 안 된다.

현재 `package.json`의 `check`와 `.github/workflows/ci.yml`에는 파티 테스트 실행이 포함되어 있지 않다. 기존 12개가 통과해도 클라이언트 재연결·IME·PiP·비동기 경합은 검증되지 않는다. 다음을 추가할 가치가 있다.

- 이전 연결이 살아 있는 상태의 재연결, `JOIN_RATE_LIMITED`·저장 실패 후 자동 복구, 같은 사용자 여러 탭.
- JOIN/CHAT 저장을 10초 이상 지연시켰을 때 닉네임·공지·메시지의 일관성.
- 닉네임 HTTP 응답 전에 페이지 이탈, 서로 다른 방으로 같은 소켓의 동시 JOIN, 초기 방 조회의 늦은 실패.
- 관전 전환과 순서 변경의 동시 요청, 입장 공지·캐릭터·순서 저장 중 연결 종료.
- 동일 메시지 재전송, ACK 유실 후 복구, 최근 기록 범위 밖의 미확정 메시지 대조.
- 새 방에서 301건 수신 후 과거 조회, 과거 조회 후 장시간 메시지 누적, 같은/다른 세션 재연결.
- 실기기 조합 중 Enter·전송 버튼·키보드 열기/닫기·멀티윈도우 전환과 PiP 닉네임 오류 복구.
