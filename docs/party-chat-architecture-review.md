## 요약

- **운영에서 보이는 증상의 대부분은 구현 결함으로 설명된다.** 배포본은 WS 라우트가 `reconnectToken`을 서버 로직에 넘기지 않는다. 그래서 재연결 토큰 기능이 운영에서 한 번도 동작하지 않았다. 실제 웹소켓 어댑터로 재현했다.
- 그 결과 배포본에서는 짧은 끊김마다 **다른 참가자로 다시 입장**하고 퇴장·입장 알림이 한 쌍씩 쌓인다. 서버가 이전 연결을 아직 모르는 상태에서 재연결하면 `NICKNAME_TAKEN`이 나서, 클라이언트가 **대화를 지우고 닉네임 입력 화면으로 쫓겨난다.** 사용자가 말하는 "튕김"과 가장 잘 맞는 경로다.
- 연결 유지 장치 자체는 정상이다. 앱 PING 없이 130초 동안 가만히 있어도 서버 heartbeat만으로 연결이 유지됐다. 서버나 프록시가 정상 연결을 끊는 결함은 찾지 못했다.
- **미배포 커밋 `a697324`는 위 결함을 모두 고친다.** 같은 프로브에서 모든 시나리오가 의도대로 동작했다. 구조 개선과 별개로 먼저 배포할 가치가 있다.
- DB는 이 기능의 정확성에 필수가 아니다. 지금 DB가 주는 것은 "배포·재시작 뒤에도 대화 기록 유지"와 "300개보다 오래된 기록 조회"뿐이다. 반면 모든 입장·채팅이 DB 쓰기를 기다리도록 되어 있어서, 서버 코드에 있는 경합 방어 코드 대부분이 이 때문에 생겼다.
- 재작성은 증상을 고치는 데는 필요 없다. 하지만 "메모리를 원본으로 두고 상태 변경을 동기적으로 처리"하는 구조로 서버 핵심과 클라이언트 연결 계층을 다시 쓰면 복잡도를 크게 줄일 수 있다. 화면 UI까지 전면 재작성할 근거는 없다.

## 2. 네트워크 단절인가, 구현 결함인가

### 2.1 프로브 결과

| 시나리오 | 배포본 `941201f` | 미배포 `a697324` |
| --- | --- | --- |
| 앱 PING 없이 130초 유휴 | 연결 유지, 알림 없음 | 연결 유지, 알림 없음 |
| 끊긴 뒤 1.5초 만에 토큰으로 재연결 | **다른 참가자 ID**, 끊긴 즉시 퇴장 알림, 1.5초 뒤 입장 알림 | 같은 참가자 ID, 알림 없음 |
| 서버가 이전 연결을 아직 살아 있다고 보는 상태에서 재연결(조용한 단절) | **`ERROR(NICKNAME_TAKEN)`** | 같은 참가자로 넘겨받음, 이전 소켓은 `1000 replaced-by-reconnect`로 정리, 알림 없음 |
| 명시적 퇴장 `close(1000, 'leave-room')` | 2~4ms 뒤 퇴장 알림 | 4ms 뒤 퇴장 알림 |
| 끊긴 뒤 재연결하지 않음 | 2ms 뒤 퇴장 알림 | 10,005ms 뒤 퇴장 알림 1회 |

### 2.2 확인된 구현 결함(배포본)

**D1. 재연결 토큰이 서버 로직에 전달되지 않음.** 배포본 `server/routes/ws/party.ts`의 `handleJoin`은 `joinPartyRoom`에 `roomId`, `nickname`, `characterId`, `order`만 넘긴다. 클라이언트는 `reconnectToken`을 보내고 서버 로직(`room.reconnectTokens`)도 토큰을 처리할 준비가 되어 있지만, 그 사이에서 값이 사라진다. 그래서 토큰 기반 승계는 운영에서 한 번도 실행되지 않았다. `a697324`에서 `reconnectToken: data.reconnectToken` 한 줄이 추가되어 고쳐졌다.

**D2. 조용한 단절 뒤 재연결이 사용자를 쫓아냄.** 와이파이와 LTE 전환, 노트북 절전, 모바일 백그라운드에서는 브라우저가 소켓을 잃어도 서버가 바로 알지 못한다. 서버는 heartbeat 만료(30초 간격 검사, 90초 기준)까지 **최대 약 2분** 동안 이전 연결을 살아 있다고 본다. 이 사이에 클라이언트가 같은 닉네임으로 재연결하면 D1 때문에 `NICKNAME_TAKEN`이 난다. 배포본 클라이언트는 이 오류를 최종 실패로 처리한다(`FATAL_JOIN_ERROR_CODES`). 그래서 `stopped = true`가 되고 `messages = []`로 대화를 비우며, 페이지의 `watch(errorCode)`가 닉네임 모달을 연다. 같은 닉네임으로 다시 들어가려 해도 이전 연결이 정리될 때까지 계속 거절된다. 결국 닉네임을 바꿔 "다른 사람"으로 들어오게 되고, 약 2분 뒤 이전 닉네임의 퇴장 알림이 뜬다.

**D3. 모든 연결 종료를 즉시 퇴장으로 처리.** 배포본 `removePartyConnection`은 연결이 닫히면 바로 퇴장 알림을 저장하고 방송한다. 재연결은 D1 때문에 새 참가자로 처리되어 입장 알림이 다시 뜬다. 1초짜리 끊김도 알림 한 쌍을 만든다.

**D4. 재연결이 입장 횟수 제한을 소모.** 토큰이 인식되지 않으니 `knownReconnect`가 항상 거짓이다. 그래서 모든 재연결이 IP당 1분 12회의 입장 예산을 쓴다. 연결이 자주 흔들리거나 같은 공인 IP(PC방, 통신사 NAT)를 쓰는 사용자가 많으면 `JOIN_RATE_LIMITED`에 걸릴 수 있다.

### 2.3 결함이 아닌 것으로 확인한 부분

- **서버 heartbeat:** 실제 어댑터에서 서버의 WebSocket ping과 pong 수신이 동작해, 앱 메시지 없이도 130초 넘게 유지됐다(두 버전 모두).
- **종료 코드 전달:** `crossws`가 close 코드와 사유를 그대로 넘겨서, `leave-room` 명시적 퇴장 판별이 실제로 동작한다.
- **nginx:** `/ws/party`의 `proxy_read_timeout 120s`는 유휴 기준이다. 서버 ping(30초)과 클라이언트 PING(20초)이 더 짧아서 타임아웃이 걸리지 않는다.
- **클라이언트 heartbeat:** PING 두 번에 응답이 없고 55초 동안 아무것도 받지 못해야 끊는다. 서버의 모든 메시지가 카운터를 초기화하므로, 백그라운드 타이머가 1분 간격으로 느려져도 정상 연결을 끊지는 않는다(코드 분석 기준).
- **제한값:** 연결당 1분 60개 메시지, 전송 버퍼 1MiB는 일반 사용에서 닿기 어렵다.

### 2.4 아직 모르는 것

- 실제로 연결이 끊기는 빈도와 원인. 서버가 종료 코드를 기록하지 않아 운영 데이터가 없다. 비정상 종료(1006), `heartbeat-timeout`, `backpressure`, `message-rate-limit`을 구분하는 로그가 필요하다.
- 실제 브라우저에서의 동작: Chrome 백그라운드 탭 정지(freeze), iOS Safari 백그라운드, Document PiP 창을 띄운 상태의 원래 탭 처리
- 배포·재시작 순간: 서버 메모리의 토큰이 사라져 모든 사용자가 새 참가자로 다시 입장한다. 두 버전 모두 같다.

**판단:** 사용자가 겪는 현상은 "네트워크가 자주 끊긴다"기보다 "끊김 자체는 평범한 수준인데, 구현이 그 끊김을 퇴장·입장 반복과 강제 퇴장으로 키웠다"로 보는 것이 근거에 맞다.

## 3. 미배포 커밋 `a697324` 평가

D1~D4를 모두 고치고, 프로브에서 각 시나리오가 의도대로 동작했다. 남는 한계는 다음과 같다.

- 유예 시간 10초: 재연결 대기 간격이 1초, 2초, 4초, 8초로 늘어나서, 네트워크가 약 7초 넘게 끊기면 재연결 성공이 약 15초 시점이 되어 유예를 넘긴다. 이 경우 퇴장·입장 알림이 한 번씩 뜬다.
- 서버 재시작 때는 토큰이 사라진다(2.4).
- 코드 규모: `server/utils/party-chat.ts` 1,358줄, `app/composables/party-chat.ts` 726줄. 경합 방어 코드와 상태 플래그가 많아 이후 수정 비용이 크다(4.2, 5).

**판단:** 구조 개선 여부와 관계없이 먼저 배포할 가치가 있다. 운영에서 확인된 결함을 고치기 때문이다.

## 4. DB가 필요한가

### 4.1 DB가 하는 일

| 기능 | DB 없이 가능한가 |
| --- | --- |
| 최근 300개(256KiB) 기록을 입장 시 전달 | 가능. 이미 메모리에서 전달한다 |
| 300개보다 오래된 기록 조회(`HISTORY`) | 메모리 보관 한도를 늘리면 부분적으로 가능 |
| 배포·재시작 뒤 대화 기록 유지 | 불가능 |
| 캐릭터·순서 변경을 과거 메시지에 반영 | 가능. 이미 메모리에서 `syncParticipantMessages`로 처리한다 |
| 다른 기능과의 데이터 공유 | 해당 없음. `party_chat_*` 테이블은 파티 채팅 모듈만 쓴다 |

방은 마지막 참가자가 나간 뒤 3분이 지나면 DB 기록까지 삭제된다. 데이터 수명이 원래 짧고, 관리자 조회나 신고 같은 다른 용도도 없다.

### 4.2 DB가 만드는 비용

- **모든 상태 변경이 DB를 기다림:** 채팅은 `INSERT`가 끝난 뒤에야 방송된다. 입장은 방 쓰기 큐 안에서 `addParticipant`, `updateParticipant`, `extendRoom`과 입장 알림 저장을 차례로 기다린다. 퇴장도 알림 저장을 기다린다.
- **복잡도의 주된 출처:** Node는 한 스레드에서 실행되므로, 메모리만 바꾸는 동기 코드는 중간에 끼어들 틈이 없다. 지금 코드에 있는 방 쓰기 큐(`queueRoomWrite`)와 await 뒤 재검증(`roomLost`, `isCurrentConnection`, `currentOwner` 재확인, `consumeBudgetOnce`), `replacedByTakeover`, 유예 타이머의 세대(`generation`) 검사는 대부분 **상태 변경 중간에 DB await가 끼어 있어서** 필요해진 것이다.
- **장애 전파:** DB가 느리거나 실패하면 입장과 채팅이 `STORAGE_UNAVAILABLE`로 실패한다. DB 연결 풀(`max: 5`)은 사이트 전체와 공유한다.

### 4.3 선택지

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. 현재 유지(DB 쓰기 후 방송) | 변경 없음, 재시작 뒤 기록 유지 | 복잡도와 DB 의존 유지 |
| B. 메모리를 원본으로, DB는 뒤에서 비동기 저장 | 상태 변경이 동기적이라 경합 코드가 사라짐, 재시작 뒤 기록 유지 | 저장 실패·순서 처리용 작은 저장 큐가 필요, 재시작 직전 몇 초 분량은 유실될 수 있음 |
| C. DB 제거, 메모리만 사용 | 가장 단순함, DB 장애와 무관 | 배포·재시작 때 모든 방과 기록이 사라짐, 오래된 기록 조회 한도가 메모리 크기에 묶임 |

**판단:** 정확성을 위해 DB가 필요하지는 않다. DB를 남긴다면 상태 변경 경로에서 빼야 한다(B). 배포 때 기록이 사라져도 괜찮다면 C가 가장 단순하다. 어느 쪽이든 A보다는 낫다. B와 C 중 무엇을 고를지는 "배포 후에도 대화 기록이 남아야 하는가"라는 제품 결정에 달려 있다.

## 5. 재작성 여부

### 5.1 판단

- 증상 해결에는 재작성이 필요 없다. 원인은 구현 결함이었고 `a697324`가 고친다.
- 다만 지금 구조를 유지하면, 앞으로 기능을 바꿀 때마다 경합 방어 코드를 계속 늘려야 한다. 이건 4.2에서 본 "DB await가 상태 변경 중간에 낀 구조"와 "참가자와 연결이 한 객체에 묶인 구조"에서 오는 문제여서, 부분 수정으로는 줄어들지 않는다.
- 따라서 **서버 채팅 핵심(`server/utils/party-chat.ts`, `server/routes/ws/party.ts`)과 클라이언트 연결 계층(`app/composables/party-chat.ts`)은 다시 작성할 근거가 있다.** 페이지 UI, PiP, 입력 처리, 캐릭터 API는 그대로 둔다.

### 5.2 다시 작성할 때의 목표 구조

1. **메모리가 원본:** 방, 참가자, 메시지 상태 변경은 모두 동기 함수로 처리하고, 저장은 그 뒤에 따로 한다(선택지 B 또는 C).
2. **참가자 세션과 연결 분리:** 토큰으로 식별되는 참가자 아래에 소켓이 0개 이상 붙는다. 소켓이 0개가 되면 유예를 시작하고, 유예가 끝나면 퇴장한다. 넘겨받기, 새로고침, 다른 탭이 한 규칙으로 처리된다.
3. **방별 순번:** 메시지마다 증가하는 순번을 매기고, 재연결 때 마지막으로 받은 순번 이후만 받는다. 지금처럼 최근 기록을 통째로 받아 합칠 필요가 없어지고, 빠진 메시지 없이 이어진다.
4. **중복 전송 방지:** 참가자와 `clientMessageId` 조합으로 중복을 막는다. DB를 쓴다면 고유 제약으로 보장한다.
5. **클라이언트 상태 머신:** `stopped`, `disposed`, `autoReconnectSuspended`, `recovering`, `documentTerminating`, `retryNotBefore` 조합 대신 명시적인 상태와 전이로 바꾼다.
6. **관측:** 연결 종료 코드·사유와 재연결 결과를 서버 로그로 남긴다.
